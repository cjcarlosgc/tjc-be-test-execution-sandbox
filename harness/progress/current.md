Revisar cada ítem contra el código expuso dos huecos reales, ahora cerrados:

- **Deadline global de ejecución** (`SANDBOX_EXECUTION_DEADLINE_MS`, default 10 min): antes solo existían timeouts por etapa (install/test) sin un techo agregado. `ExecutionPipelineService` ahora calcula un `deadlineAt` al iniciar y lo usa para (a) cortar antes de arrancar una etapa si ya no queda presupuesto (`TIMED_OUT`/`EXECUTION_DEADLINE_EXCEEDED`) y (b) acotar el timeout efectivo de cada llamada a `ContainerRunner` sin poder ampliarlo (`clampTimeout`).

Cerrado el hueco de disco temporal documentado arriba: dado que se preparaba una prueba local con Docker Desktop (storage driver `overlay2`, sin soporte para `HostConfig.DiskQuota`), se agregó una guarda de disco a nivel de aplicación en vez de dejarlo solo como limitación documentada. `WorkspaceManager.calculateDirectorySize()` mide recursivamente el tamaño real en disco de un directorio (sin seguir symlinks, para no entrar en ciclos con el layout de `node_modules` de pnpm; devuelve 0 si el directorio ya no existe). `ExecutionPipelineService` la invoca una vez, justo después de que `pnpm install` termina con éxito y antes de arrancar `RUNNING_TESTS`; si el workspace excede `SANDBOX_MAX_WORKSPACE_BYTES` (nuevo config, default 2 GiB) falla la ejecución con `WorkspaceDiskLimitExceededError` (`WORKSPACE_DISK_LIMIT_EXCEEDED`/`INFRASTRUCTURE`) sin llegar a correr ningún test. Limitación residual, intencional y documentada: la medición es puntual (una sola vez tras la instalación), no continua durante `RUNNING_TESTS` — un test que genere una cantidad enorme de archivos en tiempo de ejecución no dispararía esta guarda; el límite de tiempo/CPU/memoria del container sigue siendo la defensa para ese caso.

Verificado: lint/build en verde; 118 tests unitarios (agrega 3 casos en `WorkspaceManager.calculateDirectorySize` y 1 caso de `WORKSPACE_DISK_LIMIT_EXCEEDED` en el pipeline) y 16 e2e con Docker real (Docker Desktop confirmado arriba vía `docker info`).

Al preparar el arranque local real (levantar el Sandbox con `pnpm start:dev` y un `app/.env` real, en vez de solo la suite de tests con `ConfigService` falsos), aparecieron dos huecos reales que ningún test anterior ejercitaba, porque todos los `fakeConfigService` de las pruebas devuelven literales JS ya tipados (nunca strings de un `.env` real):

1. **`SANDBOX_WORKSPACE_ROOT=` vacío en `.env.example`/`.env` no caía al default.** `resolveSandboxLimits` usaba `configService.get('SANDBOX_WORKSPACE_ROOT', DEFAULT)`, pero el valor por defecto de `ConfigService.get` solo se aplica cuando la clave está *ausente*, no cuando está presente con string vacío — que es justo el patrón documentado ("dejar vacío para usar el default"). Resultado: `GET /health/ready` reportaba `workspace: unavailable` (`fs.mkdir('')` falla) apenas se arrancaba con el `.env.example` tal cual. Corregido con un fallback explícito por truthiness (mismo patrón ya usado en `docker-client.provider.ts` para host/socketPath).
2. **Límites numéricos de container llegaban como string al daemon de Docker.** `ConfigService.get<number>(key, default)` no convierte en tiempo de ejecución — el genérico es solo una anotación de TypeScript; un valor real de `.env` siempre es string. Con un `.env` real cargado (antes solo pasaba con literales JS en tests o variables sin definir), `SANDBOX_CONTAINER_MEMORY_BYTES` viajaba como `"268435456"` hasta el JSON que dockerode manda al daemon, que lo rechazaba: `(HTTP code 400) bad parameter - invalid JSON: json: cannot unmarshal string into Go struct field HostConfig.HostConfig.Resources.Memory of type int64`. Toda ejecución fallaba en `INSTALLING_DEPENDENCIES` con `UNKNOWN` apenas se usaba un `.env` real. Se creó `getNumberConfig()` (coerción explícita con `Number()`, con fallback al default si el valor está vacío/ausente/no numérico) y se aplicó en los siete puntos del código que leían un número desde `ConfigService`: `sandbox-limits.config.ts` (los diez campos numéricos), `container-limits.config.ts` (memoria/CPU/PIDs/timeouts/output), `docker-client.provider.ts` (puerto), `workspace-sweeper.service.ts` (intervalo) y `executions.service.ts` (`pollAfterMs`, que además viaja en la respuesta HTTP a Core — antes rompía el contrato tipando un string donde INTEROP exige `number`).

Verificado con `pnpm start:dev` real: `GET /health/ready` pasa de `503`/workspace no escribible a `200 ready` con los tres checks en verde; un `POST /executions` real contra el `.env` sin tocar ya no muere en `INSTALLING_DEPENDENCIES`. Lint/build en verde; 126 tests unitarios (agrega `get-number-config.spec.ts` y `sandbox-limits.config.spec.ts`) y 16 e2e con Docker real.

Durante sus propias pruebas locales, Core reportó un hueco real: cuando el snapshot de un proyecto viene envuelto en una única carpeta contenedora de nivel superior (patrón común de exports de GitHub, `zip -r carpeta/`), `readPackageJson`/`hasAnyConfigFile`/`hasPnpmLockfile` — que asumen el proyecto directamente en la raíz del workspace — no encontraban nada, y la ejecución fallaba con `UNSUPPORTED_PACKAGE_MANAGER`/`UNSUPPORTED_RUNNER` aunque el proyecto fuera perfectamente válido. Siguiendo la sugerencia de Core, la corrección se centralizó en `SafeArchiveExtractor` en vez de parchear cada chequeo por separado: `flattenSingleTopLevelDirectory()` corre al terminar `extract()` y, si la raíz del workspace quedó con una única entrada de nivel superior y esa entrada es un directorio, mueve todo su contenido un nivel arriba y elimina la carpeta contenedora ya vacía. Con esto, todos los consumidores downstream (los tres chequeos anteriores y también `ArtifactMaterializer`, que resuelve `relativePath` de artefactos directamente contra la raíz del workspace) siguen pudiendo asumir una estructura plana sin reimplementar la detección cada uno. No se aplana cuando hay múltiples entradas de nivel superior (proyecto ya plano) ni cuando la única entrada es un archivo, no un directorio.

Verificado: lint/build en verde; 129 tests unitarios (agrega 3 casos en `safe-archive-extractor.spec.ts`: aplana carpeta única, no aplana con múltiples entradas, no aplana un archivo único) y 16 e2e con Docker real.
