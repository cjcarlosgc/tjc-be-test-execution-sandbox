SDD 1.9 no cambia el contrato neutral del Sandbox ni le traslada la implementación del agente generalista, embeddings o chunking de Core. `DEC-SBX-001` queda `APROBADO` (pnpm como package manager del servicio), desbloqueando el scaffold. Se implementa el scaffold NestJS + TypeScript en `app/` y la feature `001-execution-api` (HU08-HU12, HU14, HU19 en su fachada HTTP): `POST /executions`, `GET /executions/{id}` y `/result`, idempotencia `Idempotency-Key`/`requestId`, auth Bearer, propagación de `x-correlation-id` y `ErrorEnvelope` centralizado, con lint/build/test/e2e en verde. La ejecución real (descarga, container, runner, resultados) queda para `002`-`006`; el estado permanece `PENDING` hasta que esas features avancen el pipeline. `DEC-SBX-002` sigue bloqueando únicamente la instalación de dependencias del proyecto ejecutado en `004-container-execution`.

Se implementan `002-project-workspace` y `003-test-materialization` y se conectan a `001` mediante un `ExecutionPipelineService`: al aceptar una ejecución, en segundo plano (sin bloquear el `202`) se crea el workspace efímero por `executionId`, se descarga el `EphemeralDownloadRef` del snapshot por HTTPS con host permitido por configuración, timeout, reintentos y redirects acotados, se verifica `sha256`/`sizeBytes`, se extrae el ZIP con defensas Zip Slip/symlink/zip-bomb (`yauzl`) y se materializan los artefactos generados (`CREATED`/`MODIFIED`) en sus `relativePath` validados. Un éxito deja la ejecución en `status=stage=PREPARING` (las etapas siguientes dependen de `DEC-SBX-002` y de `004`/`005`, aún no implementadas); un fallo produce un resultado terminal `FAILED` con `SandboxFailureFact` factual (`INPUT_URL_EXPIRED`, `INPUT_DOWNLOAD_FAILED`, `INTEGRITY_CHECK_FAILED`, `INVALID_ARCHIVE`, `INVALID_ARTIFACT_PATH`) y limpia el workspace. El sweeper de residuos por TTL existe como capacidad (`WorkspaceManager.sweepExpired`) pero todavía no se programa automáticamente; esa programación queda pendiente para `008-reliability-lifecycle`. Verificado con pruebas unitarias (incluye ZIP/symlink/zip-slip reales vía `yazl`) y e2e con un servidor HTTPS real autofirmado (descarga+extracción+materialización de punta a punta), además de lint/build en verde.

Se implementa de `004-container-execution` únicamente lo no bloqueado por `DEC-SBX-002` (PENDING, cubre solo instalación de dependencias): `ContainerRunner` con dockerode crea, ejecuta un comando fijo del propio Sandbox (`node --version`, nunca del proyecto ni de Core), aplica límites (memoria/CPU/PIDs/sin red/sin privilegios/`CapDrop ALL`), monta el workspace solo lectura, aplica timeout con `kill` y siempre elimina el container ("Docker smoke execution" de Sprint 1). Verificado con Docker real (Docker Desktop activo en esta sesión, imagen `node:22-slim` descargada): crea, ejecuta, captura `stdout` y elimina un container sin residuos. No se conecta todavía al pipeline de `001`/`002`/`003` porque hacerlo exigiría reportar `stage=INSTALLING_DEPENDENCIES` (bloqueado) o inventar un estado no contractual; queda como capacidad standalone para cuando se resuelva `DEC-SBX-002`/`005` o se exponga vía `GET /health/ready` en `008-reliability-lifecycle`. Se resolvió además un bloqueo de instalación: `pnpm-workspace.yaml` traía `allowBuilds` sin decidir para dependencias opcionales de transporte SSH de `docker-modem` (`cpu-features`, `protobufjs`, `ssh2`); se fijaron en `false` porque el Sandbox solo conecta por socket/TCP.

Se implementa `005-test-runner-adapters`: `TestRunnerAdapter` (Jest/Vitest) con `supports`/`buildCommand`/`parseResult`; un único parser normaliza el esquema JSON que Jest y Vitest comparten deliberadamente a `RunnerFacts`/`TestCaseFact`, verificado con fixtures reales (Jest 29 y Vitest 2 ejecutados de verdad: caso mixto, 100% verde y error de sintaxis). Se conecta al pipeline: tras materializar, `ExecutionPipelineService` verifica `runnerHint` contra el proyecto (config/dependencia declarada, sin instalar nada) y cierra así la verificación que `001-execution-api` había dejado diferida; una incompatibilidad produce `FAILED`/`UNSUPPORTED_RUNNER`/`CONFIGURATION`. `buildCommand` deja listo el argv de instalación futura, pero no se ejecuta: sigue bloqueado por `DEC-SBX-002`.

Con esto, las seis metas de Sprint 1 del roadmap quedan completas dentro de lo que `DEC-SBX-002` permite: esqueleto NestJS, Execution API, Object Storage access, workspace seguro, Docker smoke execution y el primer adapter Jest/Vitest (detección + parsing, sin ejecución real todavía).

Se implementa además la porción `health/readiness` de `008-reliability-lifecycle` (sin decisión bloqueante): `GET /health/live` (`200 ok` siempre, sin tocar dependencias) y `GET /health/ready` (INTEROP-1.1 §7.5), que evalúa Docker (`docker.ping()`, reutilizando el `DOCKER_CLIENT` de `004`), política de descarga (`SANDBOX_ALLOWED_DOWNLOAD_HOSTS` no vacío) y workspace escribible (`002`), devolviendo `200 ready` o `503 SANDBOX_NOT_READY` vía el mismo `ErrorEnvelope` centralizado. Sin `BearerAuthGuard` a propósito (probes de infraestructura); nunca expone hosts permitidos, secretos ni detalle interno de errores.

Se cierran los dos puntos restantes de `008` que no tenían bloqueo: `WorkspaceSweeperService` programa `WorkspaceManager.sweepExpired()` cada `SANDBOX_SWEEPER_INTERVAL_MS` (hooks nativos de Nest, sin dependencia adicional), y se agrega una prueba de fault injection que confirma que un fallo del propio `cleanup()` nunca oculta un resultado `FAILED` ya persistido. Solo queda abierto en `008` un "lifecycle state" formal más granular que `ExecutionRecord.status`/`stage`, identificado como trabajo futuro sin bloqueo.

`DEC-SBX-002` queda `APROBADO` (decisión humana): V1 soporta únicamente `pnpm` en los proyectos ejecutados, detectado por `pnpm-lock.yaml`, instalado vía `corepack pnpm@<versión fijada por configuración>` (nunca el `packageManager` del proyecto, que en la práctica trae rangos que corepack rechaza) con red acotada a esa etapa; sin red en compilación/tests. Esto desbloquea el pipeline completo: `ExecutionPipelineService` ahora encadena `PREPARING → INSTALLING_DEPENDENCIES → RUNNING_TESTS → COMPLETED/FAILED/TIMED_OUT` de verdad — `ContainerRunner` gana `installDependencies`/`runTestCommand` (generalizando el smoke check original), la instalación fallida o el timeout de cualquier etapa producen resultados factuales distintos (`DEPENDENCY_INSTALL_FAILED`/`DEPENDENCY`, `INSTALL_TIMEOUT`/`TEST_TIMEOUT` con `status=TIMED_OUT`, `TEST_EXECUTION_FAILED` si el runner no produce reporte), y un test que falla es un `COMPLETED` normal con `facts.passed=false` (el Sandbox nunca calcula `valid`, eso es de Core). Cierra además `006-execution-results` (demux, truncamiento con `originalBytes` real, `stageDurations`, `RUNNER_REPORT`/`TEST_STDOUT`/`TEST_STDERR`) y `007-batch-validation` (el conjunto de artefactos ya es el manifest, se aplica completo antes de instalar).

Verificado con Docker real y red real en esta sesión: dos pruebas e2e (`full-pipeline.e2e-spec.ts`) descargan un proyecto Vitest real por HTTPS, lo extraen, instalan sus dependencias con `pnpm` dentro de un container y ejecutan Vitest real dentro de otro — una con todas las pruebas en verde y otra con un artefacto `MODIFIED` real que hace fallar una prueba, confirmando `COMPLETED`/`facts.passed=false`. Se encontró y corrigió en el camino un bug real: `buildCommand` recibía la ruta de resultados en formato de host en vez de la ruta montada dentro del container (`/app/...`), que solo se manifestaba con Docker real — ningún test con mocks lo detectaba, evidencia de por qué vale la pena esta prueba end-to-end pesada además de las unitarias.

Con esto no queda ningún bloqueo humano pendiente conocido en este repositorio para seguir profundizando el pipeline (más adapters de evidencia, endurecimiento de `007` para casos límite, etc.); lo que sigue es alcance adicional, no decisiones.
